**What I learned**

The study site saves my answers to one file, and its server handles each request at the same time as the others. Here's the problem, in benefits terms. Two clerks open the same enrollment spreadsheet, each adds one change, and each saves. Whoever saves last wins, and the other change is gone. Nobody sees an error. That's called a **lost update**.

Claude's review tested it: fire 20 saves at once, then count what's in the file. Only 1 or 2 survived. The fix is a **lock**, the code version of checking a file out so the others wait their turn (shortened from the real `hub/progress.py`):

```python
_SAVE_LOCK = threading.Lock()

def save_task(path, *, lesson, task, done):
    with _SAVE_LOCK:                 # one save at a time
        data = load(path)            # read
        data.setdefault("tasks", {}).setdefault(lesson, {})[task] = done
        _write(path, data)           # write, before anyone else reads
```

The lock has to cover the read *and* the write. Lock only the write, and two saves can still read the same old copy.

**What was hard**

The timing. The first PR was merged before the fix was committed, so the fix couldn't ride along on the old branch. It went on a new branch and its own pull request. Then cleaning up: GitHub had "squash merged" each PR into a single new commit, so Git wouldn't delete the old branches with the safe command. I learned why. The safe delete only checks whether the branch's own commits are in main's history, and a squash merge puts the changes in a new commit instead. So we compared the files first, then used the forced delete.
